# xnote Implementation Plan

> Execution: implement in this session with independent agents for storage and editor, then integrate and verify.

**Goal:** Build an everyday local-first notes desktop application with real, interoperable Markdown and text files.

**Architecture:** React UI talks to a typed storage bridge. Electron exposes a narrow IPC API with context isolation; browser development uses an authenticated loopback service backed by the same file store. Notes remain ordinary files; preferences and favorites live in a separate application config directory.

**Tech Stack:** Electron, React, TypeScript, Vite, CodeMirror 6, react-markdown + remark-gfm, Lucide, CSS, Node filesystem, Vitest, Playwright.

## Design and choice

The workspace is empty. Node 18 is installed; Rust is unavailable. Electron is chosen over Tauri to permit immediate execution and native filesystem access in this environment. A browser-only implementation would require repeated folder permissions and would be less suitable for daily desktop use. All note operations use actual filesystem files, including browser development. There is no seeded note data.

Use three resizable columns: navigation 220px, note list 300px, generous editor. Warm gray surfaces, orange accent, native fonts, subtle borders. Empty states explain creating notes and choosing a directory. Settings use compact grouped rows. Themes follow OS or explicit preference.

## Stage 1 — foundation

Create package/build configs, shared types, typed bridge, Electron preload and main process, browser dev server, React shell and CSS. Verify TypeScript and production frontend build.

## Stage 2 — note engine and editor

Write failing filesystem integration tests first for creation, duplicate titles, reads/writes, folder operations, rename and delete. Implement FileStore with explicit supported extensions, contained paths, no symlink traversal, collision refusal, content revision checks, atomic writes and serialized operations. Implement separate CodeMirror text/Markdown editor, Markdown preview, formatting shortcuts, title editing and save state.

## Stage 3 — real filesystem and synchronization

Implement native directory picker, default Documents/xnote directory, persistent configuration, polling index refresh, optimistic revision conflict handling, directory switch and copy-first migration. Migration must preflight all conflicts, preserve source files until verified, and avoid overwrites. Test disk changes, stale writes, directory escape and collisions against temporary directories.

## Stage 4 — interaction

Connect live title/body search and highlights, folders, favorites, sorting, context menus, delete confirmations, shortcuts, font/theme/preferences and resizable columns. Before selection/directory changes, flush pending saves; on failure keep the draft available. Native close flush handshake with explicit discard confirmation.

## Stage 5 — validation and delivery

Run storage tests, TypeScript check and production build. Run browser end-to-end tests against real temporary files for create/edit/reload/search/folders/favorites/delete/theme/settings and external file changes. Launch Electron if available; verify packaging. Review safety and document commands, architecture, shortcuts, storage behavior and known platform limits in README.

## Task ownership

- Storage agent: server/store.ts and tests/store.test.ts only, shared contract in src/types.ts.
- Editor agent: src/components/NoteEditor.tsx and editor CSS only.
- Main agent: tooling, transports, desktop shell, app state, remaining components, integration, E2E and documentation.

Commands and actual outcomes will be recorded in docs/verification.md. Never describe an unexecuted native or platform test as passing.
